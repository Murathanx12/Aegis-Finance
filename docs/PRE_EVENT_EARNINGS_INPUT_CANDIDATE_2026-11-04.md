# Pre-event earnings input candidate — 2026-11-04

Offline adapter only: `backend/services/saved_earnings_calendar_input.py` accepts exact injected Finnhub `earningsCalendar` response bytes, the caller's **original** `observed_utc`, a decision `cutoff_utc`, and an exact ticker. It performs no fetch, cache read, filesystem access, model call, or runtime wiring. The existing `pm_catalysts.earnings_events` path uses `symbol`, `date`, `hour`, `quarter`, `year`, `epsEstimate`, and `revenueEstimate`. The saved [DKNG provider probe](archive/BUILD1/analyst_source_probe_DKNG.json) also shows `epsActual` and `revenueActual` on a historical row; both fields are optional here. [Finnhub's earnings calendar documentation](https://finnhub.io/docs/api/earnings-calendar) is dynamic; the sample is capture-time evidence, not a current provider guarantee.

The caller receives `EVIDENCE_ONLY` only for one exact ticker and fiscal-period row dated **1–7 calendar days after** the decision date in `America/New_York`. A selected future row with non-null `epsActual` or `revenueActual` refuses as `FUTURE_ACTUAL_PRESENT`; historical rows with actuals remain in the raw response but are not selected. Parsed actual values never enter the packet or generate beat/miss inference. The pure ET date calculation uses the US rules for 2007–2099 and refuses other eras; a future legal rule change would require review. `hour` is unverified and has no timing effect. A conservative 24-hour maximum age applies between the original observation and cutoff; a later cache hit cannot refresh it. Missing, stale, future-observed, malformed, empty, duplicate, and conflicting inputs produce explicit `REFUSED` reasons. The packet carries the exact bytes as base64, a SHA-256 of those bytes, and a deterministic context-bound `input_id`. Those hashes establish integrity, not authenticity. The packet gives no earnings direction, forecast, trading authority, or production warning delivery.

All rows for the exact ticker and fiscal year/quarter are compared before the date window is applied. Identical rows collapse; any differing row for that period refuses as `CONFLICTING_FISCAL_PERIOD`, including a past or beyond-window revision. Distinct periods outside the window may be ignored. Verification rebuilds the packet and compares canonical JSON bytes so numeric type changes and malformed packets fail. The caller must supply a defensible original observation timestamp and preserve the original packet if it later needs to compare revisions. A changed provider response is a new input, never a retroactive edit to the old observation. Production integration, capture provenance, provider coverage, and held-issuer warning behavior remain outside this candidate.

## Explicit capture candidate

`backend/services/earnings_calendar_capture.py` adds an explicit Finnhub `/calendar/earnings` GET boundary with injected transport and UTC clock. Request dates must fall 1–7 New York calendar days after the cutoff. A streamed response is capped at 256 KiB and checked against a 15-second elapsed deadline after each byte; a blocking read can extend wall time by its read timeout. The clock is sampled immediately after the full body arrives. An atomic no-overwrite publish follows temp-file fsync in a caller-specified **existing private directory**. The receipt contains the exact response bytes as base64, their SHA-256, original `observed_utc`, original cutoff, request symbol/date range, and adapter `input_id`. A response that echoes the API token is refused before persistence. `replay_earnings_calendar` reads the bounded receipt after process exit and reuses the original clock, so a later cache read cannot renew freshness. The caller must trust the private directory against same-user path replacement during capture; identity checks detect observed swaps but are not handle-bound locks. File fsync does not prove power-loss durability of the directory entry. The receipt does not prove Finnhub authenticity. This candidate has no schedule and is **not wired to the owner warning**; no delivery or decision authority follows from capture.
