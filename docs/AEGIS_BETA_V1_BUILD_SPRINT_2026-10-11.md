## 4. Reuse the weighting engine that already exists

First inspect current `backend/services/expected_return.py`, `forecast_reputation`, the planner's selection of equal versus reputation weights, the candidate PC epoch and the news admission code. Do not create a second disconnected weights module.

The inspected main source already declares ranker, revision_flow, investigator_dir, thesis_card, catalyst and source_reliability components, plus sizing-only magnitude. It computes reputation weights from eligible graded evidence, retains an equal-weight comparator and applies a planner promotion gate. It explicitly excludes `source:` and `news_digest:` from its main expected-return consumer, using old owner-decision language. This is an integration/admission/coverage problem as well as a statistical problem—not simply “there is no weights code.” Recheck the current implementation before editing.

### Required weight records

For each task/horizon/component record:

- component and source family, model/prompt version, task/target definition and horizon;
- training cutoff, feature availability clock and latest admissible outcome time;
- row count AND independent date/root-event count; missing/duplicate/quarantine counts;
- observed score versus a suitable baseline, uncertainty, decay and correlation grouping;
- prior, fitted weight, admissibility multiplier and final normalized effective weight;
- status: LEARNED, SHRUNK_PRIOR, EXPLORATORY, DISABLED, UNAVAILABLE or REJECTED, with reason;
- exact artifact hash and which subsequent forecast/plan consumed it.

No meaningful component should silently disappear. However, every component does NOT deserve positive influence: unsupported dates, invalid facts, unresolved forecasts and ineligible models remain disabled or unavailable. A justified zero weight is different from a missing implementation. Prove the mechanism updates on evidence; do not alter the data to make the update positive.

### Learning design

Prefer repairing the existing shrunk reputation estimator. Add at most one simple challenger, such as a regularized nonnegative blend trained on genuinely out-of-sample component predictions. Fit calibration and scaling only within each training window. Do not optimize a large stack of weights on nine sessions of winners.

Keep probability forecasts, expected excess returns, ranking signals, magnitude and execution-risk measurements separate. Score binary forecasts with proper losses such as Brier and log loss; compare return/rank components on their own target and costs. An analyst target's 12-month upside is not a 21-session expected return. A magnitude forecast does not become bullish merely because its prediction is large.

Update only when an outcome is actually observable. Deduplicate related source stories and repeated event/horizon rows before counting evidence. Pool thin sectors/regimes toward broader priors instead of estimating hundreds of unstable subweights. Bound changes and keep an explicit equal-weight/fixed-revision-flow fallback. Store each parameter vintage so tomorrow's prediction can be reproduced.

The new BETA_V1 experimental policy may consume its versioned admissible weights in isolated replay and paper-plan preview. If the old public-claim gate prevents the live legacy policy from switching, preserve that legacy policy; do not use its unchanged status as a reason not to finish the new experimental route. Any activation still needs its existing review and Monday constraints. Updating policy configuration is not an LLM rewriting capital code live.

### Acceptance

Using real eligible records, show the before/after weight artifact and the exact downstream forecast/ranking/plan differences. Show a no-new-outcomes rerun changes nothing. A deterministic synthetic test can demonstrate that better/worse evidence changes weights correctly, but must be labelled a fixture, not real performance. Real evidence that supports only priors must say so.
